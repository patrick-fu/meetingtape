# Qwen 录后转写的重复退化

## 现象与定位

在 Qwen3-ASR-1.7B-4bit 的分音源录后转写中，两个 30 秒麦克风块分别生成 12,289 字和 8,206 字，重复同一短词约四千次。两块原始输出的 `generation_tokens` 均为 8192，即 mlx-audio 默认生成上限。原始模型输出已有重复，因此不是 SwiftUI 重复渲染或导出拼接。

MeetingTape 每次向 Python runner 传入至多 30 秒音频，却沿用 8192 token 默认预算，未设置重复惩罚，也未检查是否耗尽预算。runner 退出成功后，任务管理器便把整个块保存为完成。这解释了异常输出为什么作为普通正文出现；尚不能从这两段样本确定声学触发原因，更不能归结为静音。原始会议音频和正文不随本报告公开。

## 修复边界

Qwen 使用轻度重复惩罚 1.1；按输入时长分配 `max(256, ceil(duration * 32))` token 预算，30 秒为 960 token。预算用于限制明显退化输出，并非宣称所有语言的最佳参数。

若生成 token 数达到预算，则保留完整原始结果和运行统计，返回明确错误与非零退出码。既有 Swift worker 因而保留此前成功进度、不把当前块标为完成，可回听或使用其他模型。不会自动删除口头禅、压缩真实重复、改写历史稿件或把截断文本当作完整结果。MOSS 和豆包解码未改动。

此判断已核对本机锁定运行时：Qwen EOS 不计入 `generation_tokens`，生成耗尽才会等于预算。上游实现：[mlx-audio Qwen ASR](https://github.com/Blaizzy/mlx-audio/blob/main/mlx_audio/stt/models/qwen3_asr/qwen3_asr.py)。

## 验证

- Python 回归测试使用生产 `transcribe` 与 `main` 边界：耗尽不能成功、短块同样受限、正常口头重复不经文本后处理删除、失败 JSON 保留 raw 且非零退出。对修改前源码执行时，耗尽与退出状态断言失败；修复后通过。
- 本机同一两段 30 秒异常音频，经修复后的 runner 实际推理，分别输出 106 token / 161 字、65 token / 92 字；不再耗尽预算。仍有少量正常口头重复。这个结果证明该重复退化在两段样本上消失，不代表全文准确率验收。
- 独立合成中文研究计划样本实际推理通过，输出包含任务、负责人和期限。另用含“嗯嗯”“这个这个”、重复短句、项目代号、金额与时间的合成语音作修改前后对照：两版均生成 42 token，重复、专名和数字内容保留，标点略有不同。这不替代多语言和大规模精度评测。
- 独立审查核对了 token/EOS 语义，以及 Swift 在保存当前块完成进度之前处理非零退出的顺序。Cursor CLI 未登录，另一渠道的跨模型复核未能运行，不记为已完成。
