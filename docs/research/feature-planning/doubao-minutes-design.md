# 豆包纪要设计与 MeetingTape 文档形态

2026-11-05。MeetingTape 基线 `81031d4f8e615f3a1159dffe811c6f30e0dd9a58`；本机豆包 2.34.6。本文为产品调研，未实现纪要生成。

## 已观测的豆包形态

以一条已有录音为样本，通过豆包客户端只读查看：

- 录音结束后，对话提供自动生成的纪要文档卡片；可打开文档或围绕录音继续提问。
- 同一文档有“纪要 / 原始记录”标签。纪要包含可编辑的内容块；原始记录显示说话人与编辑入口。本次未修改正文或播放录音。
- 样本纪要包含总结、可视化梳理、按主题组织的多级要点、带时间的章节、关键决策和金句时刻。
- 样本“关键决策”还拆出问题、讨论方案、决策依据及其他决策，兼顾结论与讨论脉络。

以上是单个样本的可见结构，不将每个模块视为所有录音必定出现的固定栏目。没有复制会议正文、标题、参与者或文档身份到本研究分支。

豆包语音官方的[语音妙记介绍](https://docs.volcengine.com/docs/doubao-voice/product-overview-13?lang=zh)另列出多层级章节、总结、流程、问答、待办等结构化能力。这是公开产品能力说明，不能据此断定桌面 App 的每条录音使用相同流水线或提示词。

## 对 MeetingTape 的含义

用户本轮明确的形态是“一场录音，一份文档”：同一文档容纳音频、纪要、字幕/翻译、各模型的独立转写版本与运行明细。选择两个或三个转写模型会增加对应版本，不应因此把一次录音变成两三份分散文档。

已有[导出约定](https://github.com/patrick-fu/meetingtape/issues/20#issuecomment-6478184033)允许主稿及其他模型/实时版本在一份导出中呈现，版本各自保留。文档作为容器，与纪要证据需要标识来源版本是两层概念：引用时记录来自哪份模型稿，界面仍是同一份录音文档。

用户本轮明确同意纪要可编辑、默认语言及独立纪要模型配置。全局设置及 BYOK 的既有交互直接沿用。此前反复询问这些基础入口应撤回；当前代码没有通用纪要模型接入，是实现状态，不能据此重问产品是否需要这些交互。

纪要内容建议以豆包的层次组织：一眼概览 → 按话题展开 → 决策和行动 → 原文回查。可视化梳理、金句、问答等按内容适用性呈现。此为研究建议，内容范围与生成时机尚未获最终确认，不将多版本文档形态擅自推导成模型裁决稿或自动混稿。

## 方式和边界

- `doubao-minutes list` 因本机该工具的登录缓存缺失而未取得结果，随后使用客户端 UI 查看；未重启豆包、启用调试端口或导出凭据。
- 静态检查只使用已安装 App 的前端包副本。解析 DataPack、解压 JavaScript、解码 JSON 字符串，未执行包中代码。
- 没有新录音、音频播放、私人会议上传或生成服务调用；没有改动产品源码、设置或网络配置。
- 旧原型覆盖录音、字幕和首次设置；明确的工单确认与本轮用户更正优先于旧原型文案。资料不足时记录范围，不能把“尚未实现”写成“尚未决定”。
